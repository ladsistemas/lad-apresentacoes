Como funciona

Da loja fechada ao pedido confirmado, em cinco chamadas

O fluxo recomendado para um bot é sempre o mesmo, seja por REST ou por MCP — e o servidor cuida da parte que importa: preço e validação.

1

Você pede um token de integração

Solicite à LAD Sistemas. Cada token pertence a uma loja só (nunca informada na URL ou no corpo — o token já resolve isso) e pode ser revogado a qualquer momento.

2

O agente consulta loja e cardápio

GET /v1/loja traz horário, formas de pagamento e pedido mínimo; GET /v1/cardapio traz produtos, tamanhos e opcionais com os IDs exatos do pedido.

3

Cota o frete e monta o carrinho

POST /v1/frete calcula o valor da entrega a partir do endereço. O agente nunca calcula preço por conta própria — só informa IDs e quantidades.

4

Cria o pedido com uma chave de idempotência

POST /v1/pedidos com um idempotencyKey (UUID) novo por pedido. Em timeout ou erro 5xx, reenvie a mesma chave: nunca duplica.

5

Acompanha até a entrega

GET /v1/pedidos/{uuid} traz o status atual — não há push, então o agente faz polling (sugestão: a cada 60s ou quando o cliente perguntar).

Duas formas de integrar

API REST tradicional ou servidor MCP — mesmo motor por trás

São as mesmas cinco operações, os mesmos campos e as mesmas regras de negócio. A diferença é só como o seu agente descobre e chama as ferramentas.

REST + function calling

Você declara as tools

Chamadas HTTP diretas aos endpoints /v1/*. A documentação já traz os cinco schemas prontos em formato input_schema, compatível com Claude e OpenAI — é colar e usar.

curl -s https://api2.laddelivery.com.br/v1/loja \
  -H "Authorization: Bearer SEU_TOKEN"

curl -s -X POST .../v1/pedidos \
  -H "Content-Type: application/json" \
  -d '{"idempotencyKey":"uuid...", "tipo":"DELIVERY", ...}'
Servidor MCP

O agente descobre sozinho

Aponte o cliente MCP para o endpoint abaixo com o mesmo token — as cinco tools (consultar_loja, consultar_cardapio, cotar_frete, criar_pedido, consultar_pedido) aparecem via tools/list, sem declarar nada na mão.

{
  "mcpServers": {
    "lad-delivery": {
      "type": "http",
      "url": "https://api2.laddelivery.com.br/mcp",
      "headers": { "Authorization": "Bearer SEU_TOKEN" }
    }
  }
}
// Streamable HTTP, stateless — sem sessão pra gerenciar

Confiabilidade

Construído pra um agente errar pouco — e se corrigir sozinho

Preço, validação de item e duplicidade são responsabilidade do servidor, não do prompt do seu agente.

  • ✓ O servidor calcula todo preço a partir do cardápio oficial — o agente nunca envia nem promete valor por conta própria.
  • ✓ Sempre envie um idempotencyKey novo por pedido: reenviar após timeout/erro 5xx nunca duplica.
  • ✓ Erros voltam em JSON estruturado (código, título, descrição) escritos para o LLM ler e se autocorrigir.
  • ✓ Token por loja, com rate limiting próprio (REST: 5 req/s · MCP: 20 req/s por token, por padrão).
  • ✓ Cardápio com cache de até 30 min, mas o preço cobrado é sempre o vigente no momento do pedido.
  • ✓ Sem cancelamento via API — cancelamentos são feitos pela loja.

Dúvidas frequentes

Perguntas de quem vai construir o agente

Preciso declarar as ferramentas na mão?

Só se for usar REST puro com function calling — e mesmo assim a documentação já traz os cinco schemas prontos em formato input_schema. Pelo servidor MCP, nem isso: o agente descobre as tools sozinho via tools/list.

O agente pode cobrar o cliente com um preço errado?

Não. O agente nunca envia preço em criar_pedido — o servidor calcula item, frete e total a partir do cardápio oficial, e a resposta é sempre a fonte da verdade a confirmar com o cliente.

Funciona com Claude, GPT ou qualquer outra IA?

Sim. O servidor MCP usa Streamable HTTP, um transporte padrão do protocolo, compatível com qualquer cliente MCP (Claude, Cursor etc.). Para quem prefere function calling manual, os schemas da documentação já vêm no formato usado por Claude e OpenAI.

Preciso manter sessão com o servidor MCP?

Não. É stateless: cada requisição é autenticada só pelo header Authorization, sem Mcp-Session-Id. GET (stream SSE) e DELETE (encerrar sessão) respondem 405 porque não existe nem stream nem sessão para gerenciar.

O agente pode cancelar um pedido pelo cliente?

Não — hoje não existe endpoint de cancelamento via API; cancelamentos são feitos pela loja. Se o cliente pedir, oriente o agente a instruir que ligue direto para a loja.

Como o agente sabe se o pedido já saiu pra entrega?

Não há push de status: o agente consulta GET /v1/pedidos/{uuid} por polling — sugestão a cada 60 segundos ou quando o cliente perguntar. O status D (Entregue) pode ser marcado automaticamente cerca de 5h após sair para entrega.

Como eu pego um token?

Solicite um token de integração à LAD Sistemas. Cada token é vinculado a uma única loja e pode ser revogado a qualquer momento — não é preciso (nem é possível) informar a loja em cada chamada.
